# ADR-0001

# Repository Governance

**Status**

Accepted

**Date**

2026-08-06

---

# Context

Feeligrane began as an open-source browser extension for annotating affective patterns in long-form writing.

During its initial design, an architectural issue quickly emerged.

Neither human contributors nor AI assistants can reliably depend on conversational memory to preserve a project's history.

Important decisions risk remaining trapped inside conversations rather than becoming part of the repository itself.

As a consequence, the repository could progressively lose coherence despite containing complete source code.

The project therefore required an explicit governance model.

---

# Problem

How can a software project remain understandable, coherent and maintainable over time when contributors include both humans and multiple AI assistants with limited conversational continuity?

The repository must itself become the project's institutional memory.

---

# Decision

Feeligrane adopts a documentation-first governance model.

The repository is designed as a structured knowledge system rather than as a simple collection of source files.

Knowledge is organised according to a normative hierarchy.

Higher-level documents define enduring principles.

Lower-level documents implement them.

Every durable decision shall eventually exist inside the repository.

Conversation history is considered transient.

Repository history is authoritative.

---

# Normative hierarchy

The project currently recognises the following hierarchy.

```
CONSTITUTION.md
        │
SESSION_BOOT.md
        │
Architecture Decision Records
        │
Methodological documentation
        │
Technical documentation
        │
Roadmap
        │
Source code
```

Doctrine exists outside this hierarchy.

It is intentionally non-normative.

Its purpose is to develop ideas before they become decisions.

---

# Governance principles

The repository should remain understandable without privileged historical knowledge.

Contributors should recover context by reading documentation rather than reconstructing conversations.

The project therefore separates several complementary functions.

| Function | Primary document |
|----------|------------------|
| Identity | CONSTITUTION.md |
| Working protocol | SESSION_BOOT.md |
| Architectural memory | ADRs |
| Project presentation | README.md |
| Reflection and future ideas | doctrine.md |
| Project evolution | CHANGELOG.md |

Each document answers one primary question.

Documentation should remain complementary rather than redundant.

---

# Consequences

Positive consequences:

- Reduced dependence on conversational memory.
- Better continuity between contributors.
- Explicit architectural memory.
- Clear separation between principles, procedures and implementation.
- Improved long-term maintainability.

Trade-offs:

- Documentation requires continuous maintenance.
- Architectural discipline becomes part of development work.
- Contributors must understand the normative hierarchy before introducing significant changes.

---

# Future evolution

The following developments are considered compatible with this decision.

- PROJECT_CODE.md as an automatically generated consolidated view of active rules.
- PROJECT_STATE.md as an operational snapshot of the project.
- Automated constitutional consistency checks.
- Automated documentation consistency checks.
- Cross-references between constitutional principles, ADRs and methodological documents.

These features extend this governance model without changing its underlying principles.

---

# Alternatives considered

## Conventional repository

A traditional repository relying primarily on source code and README documentation.

Rejected because architectural knowledge would progressively migrate into conversations.

---

## AI memory as primary continuity mechanism

Relying on persistent AI memory.

Rejected because contributors, tools and models change over time.

The repository must remain self-sufficient.

---

## Extensive wiki

Using an external wiki as the primary knowledge base.

Rejected because governance should remain versioned together with the code.
